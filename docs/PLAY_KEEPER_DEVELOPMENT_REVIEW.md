# 从四个 WebView 到跨设备任务编排：Play Keeper 的开发复盘

> 一款个人自动化工具，如何在真实使用中逐渐遇到状态一致性、故障恢复和多用户隔离问题。
>
> 本文依据截至 2026 年 10 月 20 日的本地源码、版本记录和用户反馈整理。代码基线为 `187b66a`，APP 与 VPS 版本为 `2.0.2-rc6`。这是工程复盘与优化建议，不是本轮真机验收报告；文中建议均不代表已经实现。

## 一、起点很简单，复杂度却来自流程之间

Play Keeper 最初要解决的问题很直接：在 Android 上保留多个相互隔离的网页账号，让用户能够持续运行网页，并在远程查看和操作。

此时，主要挑战是 WebView 会话隔离、横竖屏切换、页面恢复、黑屏遮罩与设备状态上报。随着需求增加，系统逐步加入拍卖、装备转移、签到、日常任务、副本队列、定时运行和多用户管理。

变化的关键不是按钮越来越多，而是一个动作开始依赖另一个设备上的结果：

卖方上架以后，买方要购买；买方收到装备以后，卖方要停止刷新、穿戴剩余装备并回到挂机地图；买方完成副本以后，又成为下一段转移的卖方。

因此，Play Keeper 已经不只是一个“帮用户点击网页”的容器，而是一个由 Android 执行端、VPS 调度端和浏览器控制台组成的跨设备任务系统。网页本身，则是这个系统无法控制加载速度与页面结构的外部依赖。

**项目后半程的核心问题，从“怎么点击成功”，变成了“如何确认成功、如何交接控制权、失败以后从哪里继续”。**

## 二、开发历程：从功能验证走向可靠性建设

| 阶段 | 主要演进 | 新出现的工程问题 |
|---|---|---|
| 早期至 v1.0 | 多账号 WebView、远程截图与点击、黑屏保护 | 会话隔离、资源占用、生命周期恢复 |
| v1.1—v1.8 | 道具拍卖、装备交易、五件分批、穿戴与副本 | 页面加载竞态、错误控件、交易结果复核 |
| v1.9 | 双设备八账号接力、每日状态、背包汇总 | 账号与设备映射、跨设备交接、执行进度追踪 |
| v1.10 | 人工介入、状态持久化、指定装备所在账号恢复 | 已完成步骤如何跳过、路线如何保持、迟到错误如何处理 |
| v2.0—v2.0.1 | 多用户登录与设备归属、自定义路线、套装模板、滑动 | 用户隔离、配置迁移、不同入口行为一致性 |
| v2.0.2 RC 系列 | 设备归属修复、卖方收尾、诊断文档、重复恢复修复 | 从局部功能通过，转向整条流程可恢复、可验证 |

这条演进路线体现了原型开发的优势：需求来自真实场景，反馈具体，修复能够直接回应使用障碍。截图、错误控件名称和运行记录，让开发不必完全依赖猜测。

项目也已经建立了一些值得保留的基础：装备名称与批次规则测试、设备归属持久化、账号级配置、命令白名单、人工确认恢复，以及按用户下载的报错说明。

但版本记录也揭示了一个信号：“卖方返回挂机”“装备交接后继续下一账号”“中断后恢复”等问题曾在多个版本中重复出现。这不等于每次修复都没有作用，而是说明同一个业务目标存在多条执行路径，局部修复尚未形成覆盖所有路径的统一约束。

## 三、反复报错背后的四个工程问题

### 1. 点击成功，不等于业务成功

`no_sell`、`no_dialog` 和“未检测到背包数量变化”，看起来是页面定位失败，背后却可能是完全不同的状态：

- 页面还在加载，卖出按钮尚未出现；
- 装备已经上架，页面显示的是“下架商品”；
- 提交已被网站接受，但列表还没刷新；
- 当前批次达到五件限制；
- 操作进入了错误的页面或弹窗。

这些情况不应该统一处理成“再点一次”。对交易操作盲目重试，可能比停止更危险。

更可靠的方式是把每一步拆成“识别前置状态 → 执行动作 → 观察结果 → 必要时核对恢复”。等待应以页面状态为条件，并设超时上限，而不只是不断增加固定延迟。

当前代码还暴露出一个需要优先审查的验收缺口：`repairAndVerifyTargetEquipment()` 会检查已占用槽位数量，但传给装备审计的槽位名称映射来自预期装备清单，而不是逐槽读取到的实际装备名称。购买记录和槽位数量虽然提供了部分证据，却不足以证明目标套装确实穿在目标宠物上。

这是一项源码层面的风险发现，不能直接认定为某次线上故障的原因。建议将“预期装备”和“实际观察到的装备”彻底分开；无法可靠读取时显示“待确认”，不要把推断包装成已验证。

### 2. 停止任务，不只是改变一个状态字段

对于卖方返回后又进入交易所的现象，任务控制权与迟到回调是应优先排查的方向。当前异步结构存在这一风险，但具体一次运行的根因仍需日志确认。

Android 自动化包含延迟执行和网页异步回调。旧任务即使在业务上已结束，它之前安排的动作仍可能稍后返回。当前已有部分任务类型检查，但仅检查“现在是不是装备出售任务”还不够：旧的一次出售与新的一次出售，任务名称可能完全相同。

建议为每轮执行携带运行编号、转移段编号和尝试编号。每个延迟动作与回调执行前，都要确认自己仍属于当前任务；中断时统一使旧编号失效。

源码中的 `runGeneration` 目前存在递增和声明，但尚未用于回调身份比较。这说明可以沿现有结构补齐取消机制，不必推倒重写。

### 3. 恢复应移动进度，而不是改写计划

rc6 对“确认套装账号并继续”的修复，提供了一个很有代表性的案例。

此前恢复操作会把完整路线裁成剩余片段。第一次恢复可能看似正常，但保存后的路线不再首尾闭合，下一次恢复又会被闭环校验拒绝，于是用户感觉按钮没有反应。

更合理的数据模型是：保留完整路线，用游标表示当前进行到哪一段。完成状态、当前装备持有者和运行阶段独立保存，不再通过删改路线隐式表达进度。

这里还要把恢复语义写清楚：从中间账号恢复，是继续原计划剩余部分直至终点，还是从该账号重新跑完整一圈？两者都可以设计，但必须让界面、实现和测试使用同一解释。

### 4. 多个入口，不应该各有一套收尾规则

“多用户挂机”与“当前账号高级操作”都可以触发装备转移。如果前者由 VPS 跟踪、后者只是直接发送手机指令，就容易出现“主流程会释放卖方，快捷操作却一直等待”的差异。

rc6 已为定向转移增加 VPS 协调器，这是向统一管理迈出的一步。但该协调器目前仍是独立的内存状态，尚未具备与每日计划同等的持久化和命令回执关联机制。

下一步应让不同入口调用同一套交接、取消、超时、收尾和恢复能力。入口只决定参数与权限，不决定另一套业务规则。

## 四、APP 端：先保证执行可信，再优化性能

### 执行架构

不建议为重构而全面更换语言或界面框架。更有收益的是逐步拆开当前职责较重的自动化代码：

- **页面适配层**：识别交易所、仓库、装备栏与弹窗，返回结构化观察结果。
- **任务执行层**：管理步骤、超时、重试、取消与当前任务身份。
- **业务规则层**：处理名称匹配、五件批次、价格、买家和装备验收。
- **会话与配置层**：管理账号 Profile、升级迁移和保存范围。

这样，网站页面变化主要影响适配层，路线规则变化主要影响任务层，也更容易分别测试。

### 失败策略

失败不应只有“全部停止”或“全部忽略”两个选项。

交易价格、指定买家、目标装备无法确认时，应停止并保留现场；页面暂未加载可以有限重试；报告邮件失败不应倒退装备流程。

存仓失败尤其需要细分：暂时找不到入口、仓库已满、背包已满、容量未知，是不同风险。建议显示明确警告，并由用户选择可接受的继续条件。避免从“一次 missing 阻断所有任务”，直接摆到“任何存仓失败都继续”的另一端。

### 本地体验与资源管理

APP 应始终显示当前账号、正在执行的步骤、最近一次成功时间和暂停原因。手动切换查看账号，不应被后台脚本抢回；需要人工接管时，应明确暂停哪些任务。

四个 WebView 的长期运行，要分别测量内存、渲染异常、温度和耗电。预览无人查看时停止采集，交互期间短暂提高刷新频率，比长期提高帧率更值得优先验证。

黑屏遮罩、系统熄屏和后台存活能力也应在界面中明确区分，避免用户误以为黑屏等同于应用可永久后台运行。

## 五、远程控制台与 VPS：让用户看懂，也让系统管得住

### 控制台首先要回答五个问题

1. 当前由谁向谁转移？
2. 目标套装目前在哪里，依据是什么？
3. 哪一步已经完成，哪一步还在等待？
4. 此刻可以安全执行哪些操作？
5. 点击按钮后，请求究竟处于什么状态？

建议把首页重点改为“当前任务与待处理问题”，设备指标和高级配置放在次级区域。退出进程等高风险操作不应比任务恢复更突出。

“新建计划”“从已确认账号继续”“中断计划”应明确区分。按钮旁显示“正在提交／设备已接受／执行中／完成／失败”，失败原因就地呈现，不只追加到页面底部日志。设备已接受命令也不能显示成业务已经完成。

账号角色应直接显示为“卖方 A → 买方 B”，并单独展示装备持有者。若套装分散在背包、在售列表和另一账号中，应允许显示“部分转移／待核对”，而不是强行给出唯一账号。

配置方面，应标明“本用户计划默认值”“本设备账号设置”“本次运行参数”，显示保存状态与生效范围。实时刷新不能覆盖正在编辑的表单。移动端则优先保留任务状态、当前画面和恢复操作，减少长页面来回寻找按钮。

### 多用户隔离，不等于多用户调度已经完整

当前已经有用户设置与设备归属隔离，但服务端仍分别创建一个每日计划实例和一个定向转移协调器。后续要么明确采用全局排队，并告诉用户正在等待谁；要么建设按用户组织的计划队列，并对设备、账号加互斥保护。

同一账号不应同时被定时计划、快捷交易和人工恢复控制。设备重新连接也不应改变管理员已确认的归属。

### 把报错文档升级成运行证据

按用户保留 Markdown 报错说明是很好的起点，但只记录最终错误，还不足以解释“为什么走到了这里”。

建议在后台保留结构化事件，再生成用户可读文档。事件至少关联运行、转移段、命令、尝试次数、APP/VPS 版本和设备；记录请求、接收、执行、结果确认的过程。

重复错误可以合并显示，但应保留首次时间、末次时间和次数。诊断导出要脱敏，不包含密码、令牌、Cookie 等凭据；截图也应有保留期限与用户控制。

### 安全与运维也属于产品功能

建议将默认密码限定为首次初始化用途，首次登录要求修改；设备配对凭据与控制台登录凭据分别管理，支持撤销与轮换。设备归属检查应覆盖命令、截图、日志和报告下载，而不只是在前端隐藏按钮。

VPS 升级前应备份用户配置与运行状态，迁移后验证数据完整性，并准备兼容的回退方案。网页同时显示 APP、VPS 与协议版本，减少“已更新一端、另一端仍旧”的排查成本。服务健康检查也应区分“连接在线”和“任务持续有进展”。

## 六、版本测试：围绕风险分层，而不是每次只测新按钮

当前仓库已有纯 Java 规则测试和 Node 协议、状态机测试，静态核对可见 13 个 Java 测试方法与 32 个 Node 测试定义。它们是重要基础，但这个数量不代表真机覆盖率，也不是本次重新执行后的通过报告。

目前唯一的 Android CI 工作流执行单元测试与 Release 构建，主要由手动或 `test/**` 分支推送触发；Node 测试、Lint、浏览器交互及真机验收尚未串成同一发布门禁。

测试应分为规则、组件集成、端到端几个层次。Android 官方也区分本机测试与设备测试：前者适合快速隔离验证，后者用于验证设备上的行为，两者不能互相替代。[Android 测试基础](https://developer.android.com/training/testing/fundamentals)

### 不同版本，应有不同的重点

| 版本类型 | 必测重点 | 不应接受的“通过依据” |
|---|---|---|
| 容器与兼容性更新 | Profile 隔离、旋转、渲染恢复、覆盖安装保留登录 | APK 能安装 |
| 交易规则更新 | 精确名称、强化后缀、价格、买家、五加五批次、重复提交防护 | 点击过确认按钮 |
| 跨设备流程更新 | 同设备与跨设备分别验证，延迟、乱序、离线与重连 | 两台设备显示在线 |
| 多用户与配置更新 | 用户 A/B 隔离、归属持久化、中文账号、旧数据迁移 | 当前管理员账号正常 |
| 恢复类 RC 更新 | 连续两次中断恢复、恢复后重启、旧回调迟到、全链路收尾 | 第一次点“继续”有效 |
| 正式版候选 | 完整闭环、长时运行、升级兼容、签名及制品核对 | CI 全绿 |

针对 v2.0.2，最重要的回归场景不是再测一次顺利交易，而是组合故障：

- 从中间账号恢复，再次中断，再次恢复，确认路线和顺序没有改变。
- 卖方已释放后，旧出售错误才到达，确认不会退回旧阶段。
- 买方完成购买后离线，重连时核对实际装备，不能盲目重买。
- VPS 在首批交易、第二批交易、卖方收尾期间分别重启。
- 只有“普通攻击”且技能值为 0 时，仍按实际页面状态判断能否启动。
- 已完成副本的账号只跳过副本，不被错误移出装备接力路线。
- 两个用户同时操作，既不能串设备，也不能覆盖对方任务。

测试时还应建立几个必须始终成立的约束：同一账号只有一个有效任务控制者；迟到回执不能改变新任务；未经观察的装备不能标记为已验收；恢复不能悄悄改变用户路线。

### 一条更稳妥的验收路径

先验证规则与模拟设备，再验证固定页面样本；随后进行真机只读检查、单账号操作、同设备双账号、跨设备双账号，最后才运行八账号闭环。

仓库已有八账号测试计划体现了这种逐级验证思路。应把它变成发布门槛，而不只是参考文档。涉及真实道具的测试应由用户确认范围，使用可承受损失的测试物品，不用高价值装备验证尚未确认的交易路径。

新旧版本搭配也要单独测试：APP 与 VPS 同版、旧 APP 配新 VPS、允许过渡期内的新 APP 配旧 VPS。不能兼容的组合应明确拒绝并提示升级，不能继续发送对方不认识的命令。

## 七、开发流程：从“收到截图就修复”到可重复的闭环

建议把每次修复固定为六步：

1. **记录问题**：版本、环境、路线、运行编号、预期、实际结果和现场。
2. **最小复现**：将故障缩小成两账号、一段转移或一次恢复。
3. **补失败测试**：证明旧代码确实会出错，再修改实现。
4. **分层回归**：规则测试、协议测试、页面样本、控制台交互与真机验证。
5. **发布候选版**：限定本版目标，记录兼容关系和剩余风险。
6. **用户验收后转正式版**：以完整流程和异常恢复结果为依据，而非仅以构建成功为依据。

现有 RC6 定向转移协调器只有一个正常路径测试；人工选择中间账号恢复的测试，也还没有覆盖“连续恢复后跑完整条闭环”。这些是应优先补齐的具体缺口。

版本记录宜明确使用四种状态：**代码已修改、自动测试已通过、真机局部已验证、完整闭环已验收**。不要用一个笼统的“已修复”替代全部证据。

每个 RC 应同时保存源码提交、APP/VPS 版本、包名、签名指纹、制品 SHA-256、配置版本和测试清单。候选版还应在发布平台明确标记为预发布，不能只在名称末尾加 `rc`。GitHub 提供独立的预发布标记。[GitHub 发布管理说明](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository)

跨平台开发也依赖这份清单。APK 哈希只能帮助确认拿到的文件是否一致，不能替代源码、构建环境、签名材料与迁移说明。签名私钥应安全独立保管；改变现有签名之前，必须先规划覆盖升级与数据迁移。

另一个容易忽视的维护项是文档：当前 `DEVELOPMENT.md` 和发布指南仍有 v1.7.1 与旧包名信息，而构建配置已经到 rc6。建议将历史设计记录与当前操作指南分开，把版本、包名和制品信息从构建过程自动生成，减少 Windows/macOS 接手时的误判。

## 八、下一阶段，不必先增加功能

**第一优先级是正确性。** 补齐实际装备观察、统一任务身份与取消机制、串行控制同一账号，并验证恢复与卖方收尾不会互相覆盖。

**第二优先级是可恢复、可解释。** 统一不同入口的协调能力，补齐持久化与超时处理，让按钮反馈、任务时间线和诊断记录能够解释同一件事。

**第三优先级才是体验与性能。** 在流程稳定的基础上，优化移动布局、预览采集、资源消耗和长期运行表现。

Play Keeper 最值得提炼的经验是：个人工具走向多设备、多账号、多用户时，真正需要升级的不是功能数量，而是软件对状态、证据和失败的处理方式。

一个可靠的自动化系统，不仅要在顺利时跑完，更要在中断后回答清楚：**已经完成什么、当前事实是什么、下一步为什么可以安全执行。**
