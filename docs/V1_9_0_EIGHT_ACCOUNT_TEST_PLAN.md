# Play Keeper v1.9.0：双设备八账号每日接力测试方案

本文档只定义验证顺序和验收条件。用户确认测试结果前，不修改正式 Android 自动化流程，也不启动真实装备转移。

## 1. 当前线上基线

2026-10-08 线上控制台显示两台设备在线：

- 设备1 `PK-135890B75EBC`：`hao1`、`hao2`、`hao3`、`hao4`
- 设备2 `PK-8245AB0137A6`：`hao`、`hao7`、`hao5`、`hao6`

账号在设备2上的槽位顺序不是计划运行顺序，因此后续流程必须按账号名称解析设备和槽位，不能写死 `accountIndex`。

已在不启动任何交易或副本脚本的条件下，逐一发送八个账号的远程切换命令；八次均收到“账号已切换”成功回执。测试结束后已恢复设备1前台账号为 `hao2`、设备2前台账号为 `hao6`，并停止测试预览。这证明八个账号当前均能通过远程协议激活，但不代表完整自动化已通过。

远程手机页面为按需预览：切换账号或首次进入后，必须点击绿色“加载/刷新”，并预留约 10 秒等待首帧返回；黑色占位区本身不代表白屏或设备离线。按此流程已成功看到设备2 `hao` 的背包页面。现版本仍没有只读装备扫描命令，因此尚不能可靠确认十件情改装备是否在 `hao`；装备归属必须由只读扫描测试版确认，不能通过启动“卖方上架装备”来试探。

进入真实游戏页面还必须点击口袋助手顶部的“进入主游戏”。如果出现“请将手机横屏使用”，先发送横屏命令；设备未自动旋转时再点击“手机转不动？点这里继续”。游戏页面切换存在木板开合动画，自动识别必须等待目标页面稳定，不能在过渡帧上判定失败。

设备2 `hao` 的超清画面已确认：目标装备集中穿戴在主战宠物“小红帽”的宠物资料页。首次探索曾通过“一键脱装备”在背包中读到名称，但后续测试证明该操作会波及副宠，正式测试版不再使用。未脱目标装备时看到的装备背包 `10/40` 为其他伊苏王、火龙王和法老王系列装备，不能据此判断情改装备缺失。

2026-10-08 的可恢复真机测试发现，游戏页面的“一键脱装备”并不只作用于当前主宠：在选中“小红帽”时实际提示卸下11件，除十件情改装备外还把副宠“炎龙血焰”的一件 `火龙之牙` 放入了背包。“一键穿装备”也会按槽位自动选择其他装备，曾把同槽位的 `暗夜女神·影【神】` 穿到主宠上，不能用于精确还原指定套装。因此正式每日转移禁止使用游戏页面的一键脱装/一键穿装来完成情改套装交接；现有“一键穿装备”功能保留为人工工具，但不进入每日计划的自动调用路径。

测试现场已恢复：副宠原有 `火龙之牙` 已穿回，主宠“小红帽”的十个槽位已恢复。测试当时记录到的属性为生命48972、魔法6709、攻击32176、防御17853、命中6205、闪避5856、速度6556、成长11.3；宠物合成和等级变化会使属性自然变化，因此属性只作为带时间的观察快照，不作为装备恢复或交接成功的验收基线。

测试版对 `hao` 的装备确认流程改为：选中“小红帽”主战宠物并确认穿戴区域已加载 → 仅扫描主宠十个槽位 → 复用 App 端已有的装备背包滚动读取能力，按精确名称建立十件目标装备清单 → 对十件白名单装备逐件执行。每件装备分别记录检查结果；缺件标记为“跳过”并继续检查其余项目，不重复实现现有的查找、滚动、上架和购买流程。最终只根据十件目标装备是否转移并穿入各自正确槽位判断整批成功；少一件或同槽位穿入错误装备时整批不得标记成功。副宠无论是否存在都不扫描、不脱装、不穿装、不参与转移。任何脱装后的失败或中断都必须明确标记“装备已在背包”，禁止误报为装备丢失。

## 2. 手机端退出与启动的可行性

| 操作 | 现有架构可行性 | 说明 |
|---|---|---|
| 启动每日计划 | 可行 | 两台设备在线时由中继调度器下发白名单命令 |
| 中断每日计划 | 可行 | 停止后续步骤，保留当前页面和装备现场 |
| 在线重启 Play Keeper | 可行 | App 在线时先安排本机重启，再结束当前 Activity |
| 退出 Play Keeper | 可行但危险 | 退出后 WebSocket 断开，控制台无法再命令它启动 |
| App 已离线时远程启动 | 现有架构不可行 | 需要前台服务、设备所有者、ADB 或其他常驻唤醒通道 |

正式页面建议提供“启动每日计划”“中断每日计划”“重启 Play Keeper”。如保留“退出 Play Keeper”，必须二次确认并明确提示退出后需要现场重新打开。

## 3. 每日装备闭环

装备持有路径固定为：

```text
设备2 hao
  -> 设备1 hao1
  -> 设备1 hao2
  -> 设备1 hao3
  -> 设备1 hao4
  -> 设备2 hao5
  -> 设备2 hao6
  -> 设备2 hao7
  -> 设备2 hao
```

每个接收账号的完整步骤：

1. 确认卖方、买方设备在线，账号映射存在，双方没有其他脚本运行。
2. 卖方上架第一批最多5件装备。
3. 调度器收到结构化的“第一批可购买”状态后启动买方，不能依赖固定20秒或状态文字。
4. 卖方确认成交后上架第二批；买方确认十件目标装备已购买并穿戴。
5. 买方接受日常任务，顺序运行四个副本。
6. 四个副本全部结束后读取一次背包物资快照。
7. 恢复圣兽云殿挂机。
8. 除最终 `hao` 外，当前账号成为下一棒卖方。

最后一棒 `hao` 也要运行四个副本、读取背包快照并恢复圣兽云殿，装备最终保留在 `hao`。

装备检查范围统一限定为主战宠物：

- 主账号 `hao`：固定检查主战宠物“小红帽”。起点和最终回收都只核对主宠十个槽位及十件目标装备。
- `hao1` 至 `hao7`：只检查当下主战宠物的穿戴装备。
- 副宠无论是否存在、是否有装备，都完全跳过；不得读取或修改副宠装备，也不把副宠空槽或旧装备计为异常。
- 交接验收以“当前接棒账号的主战宠物已完整穿戴十件目标装备”为准；准备下一棒时，只从当前主战宠物逐件脱下白名单内的十件目标装备，禁止调用会波及副宠或自动替换同槽装备的一键操作。
- 每件目标装备都保存 `beforeConfirmed` 与 `afterConfirmed`；十件全部通过前，整次交接不得标记成功。

## 4. 调度规则

- 整套计划全局只允许一个实例运行。
- 每日启动时间可配置；启动前必须重新解析八个账号所在设备和槽位。
- “1小时”作为单账号副本的预计耗时和告警基线，不作为盲目切换账号的定时器。
- 下一棒只能由“装备购买完成 + 四副本完成 + 背包快照完成 + 圣殿恢复完成”事件触发。
- 单账号建议软告警60分钟、硬超时90分钟；超时后暂停整套计划，不自动把装备转向下一账号。
- 中继服务必须持久化 `planRunId`、日期、当前账号、当前阶段、重试次数和最近错误，服务器重启后不能重复上架或购买。
- 跨设备步骤必须由中继调度；现有 Android 代码只能自动寻找同一设备内的买方。

预计总耗时约为8小时副本时间加8次装备交接时间，实际应预留9至10小时窗口。

## 5. 每日执行监控

控制台为每个账号显示：

- 今日装备接收：未开始 / 执行中 / 成功 / 失败
- 今日四副本：未开始 / 当前第几个 / 全部完成 / 超时
- 日常任务接受：成功 / 无可接受任务 / 失败
- 背包快照：最后刷新时间、来源和读取状态
- 副本识别状态：当前账号、识别方式、DOM探测周期、最近一次成功探测时间、页面稳定状态
- 当前账号预览：实际分辨率、目标/实际刷新率、最近一帧时间、连续丢帧数、画质档位
- 圣兽云殿：已恢复 / 未恢复
- 下一棒装备交付：成功 / 失败 / 最终账号无需交付
- 今日整套计划：未运行 / 运行中 / 成功 / 部分完成 / 失败 / 已中断

每日记录至少保留最近7天，且不能只存在浏览器内存中。

远程预览画质与自动副本识别状态必须分别显示。当前副本逻辑通过 WebView DOM 查询按钮、下拉框和文字，不是依赖远程 JPEG 画面做 OCR，所以降低网页预览画质不会直接降低副本识别准确率。控制台现有预览档位实际为“流畅720：1 FPS / 高清1280：0.33 FPS / 超清2560：0.1 FPS”；当前页面只显示画质名称，没有把对应刷新率展示给用户。超清模式约10秒才返回一帧，这也是人工查看切页动画时容易误判为卡住的原因。自动副本运行时建议固定显示例如：

```text
hao · 四副本 2/4 · 识别：DOM · 探测周期 1.0s · 最近成功 0.4s
预览：1280×544 · 高清 · 0.33 FPS · 最近帧 1.8s · 丢帧 0 · 页面稳定
```

若 DOM 探测连续失败、目标页面尚在动画中或关键控件结构变化，应暂停当前识别步骤；不得继续点击猜测。预览的实际刷新率、最近帧、丢帧和尺寸用于人工判断画面是否及时，但不能作为副本已完成的唯一依据。每次自动识别结论应记录探测时间、当前 URL、关键控件结果和页面稳定状态，方便定位误识别。

## 6. 背包物资快照

默认查询项目：

```text
进化宝石
曙光印记
强化丹A
强化丹B
天仙玉露
```

项目列表允许自定义。已在设备2 `hao` 的实时背包画面中确认游戏实际名称为“天仙玉露”，后续扫描按这个精确名称匹配；仓库旧预设中的“天仙雨露”需要同步更正。

刷新方式：

- 每个账号四副本完成后自动刷新一次。
- 控制台提供单账号手动刷新。
- 每天可配置一次定时刷新。
- 扫描只读取名称和数量，不出售、不拍卖、不存仓。
- 读取失败时保留上一条成功数据，并明显标记“本次失败”，不能把未知显示为0。

建议遥测字段：

```json
{
  "inventoryMonitor": {
    "status": "success",
    "checkedAt": 0,
    "source": "after_dungeons",
    "items": [
      { "name": "进化宝石", "count": 0 }
    ],
    "error": ""
  }
}
```

## 7. 日常任务问题与修复验收

v1.8.4 当前逻辑存在以下问题：

1. 点击“一键接受”后立即返回 `accepted`，未等待网页确认框结果。
2. 700ms 后无条件关闭任务窗口并继续副本。
3. 确认框文案必须同时包含“一键接受”和“日常任务”，实际文案变化会漏判。
4. 没有验证按钮已禁用、可接受任务数已变化或页面出现成功提示。
5. 遥测中的“已一键接受日常任务”只代表按钮已点击，不代表服务器已接受。

测试版应先记录实际弹窗类型与完整文案，再实现：

- 每账号独立的确认请求状态，不使用单纯10秒猜测窗口。
- 确认回调完成前不继续副本。
- 匹配 `sgplay.cc` 与 `www.sgplay.cc`，并对确认文案做最小但兼容的匹配。
- 确认后重新读取任务窗口，验证接受结果。
- 把结果区分为 `accepted`、`nothing_to_accept`、`confirm_missing`、`verify_failed`。
- `confirm_missing` 和 `verify_failed` 默认暂停该账号计划，不静默继续。

## 8. 分阶段测试门槛

### 2026-10-08 现有代码静态测试结果

- 默认情改清单共10件、去重后仍为10件，与用户指定名称完全一致。
- 卖方入口当前仍调用“一键脱装备”，会波及副宠，不满足“只处理主宠”的要求。
- 卖方按名称查找某件失败时当前会记录“背包无此装备”后继续下一件，可能少件交接却不立即中止。
- 买方购买结束后当前仍会先“一键脱装备”再“一键穿装备”，可能替换同槽位非目标装备。
- 买方最终校验目前只统计已填充槽位数，不验证十个精确名称；十个槽位已满但装备错误时可能误报成功。
- 当前状态只记录集合式的“已上架/已购买名称”，尚无每件装备独立的 `beforeConfirmed`、`afterConfirmed` 和失败现场。
- 中继服务现有协议测试3项全部通过，但尚未覆盖八账号计划、十件逐件确认和跨设备恢复。

结论：真实装备交易继续保持禁用。下一版测试实现必须先让上述失败条件全部变成可自动验证的测试用例，再允许单账号或双账号真机交接。

已新增纯 Java 最终验收测试，复用正式十件清单，不替换现有 WebView 查找、滚动、上架、购买和缺件跳过逻辑。当前5项测试全部通过：十件逐项成功、缺一件仍继续检查其余九件但整批不成功、副宠输入在读取前被拒绝、同槽位错误装备不通过、额外背包装备和宠物属性不影响十件结果。中继协议回归测试仍为3/3通过。该测试阶段尚未把最终验收器接入真实交易流程，也未构建或安装新APK。

### A. 纯协议和调度模拟

- 两台模拟设备、八账号映射全部通过。
- 正常闭环严格按 `hao -> hao1 -> ... -> hao7 -> hao`。
- 任一设备离线、账号忙、命令超时、重复回执、服务器重启都不会重复交易。
- 非当前计划账号不能接收交易命令。
- 中断计划后不再启动新阶段。
- 十件装备逐件产生独立结果；缺件记录为跳过后继续检查其余装备，名称或槽位不符则记录失败，最终十件未全部成功时整批不得标记成功。
- 属性变化不影响装备验收；验收只依据账号、主宠、精确装备名、槽位和交易结果。

### B. 真机只读测试版

- 八账号逐一切换并回报账号名。
- `hao` 选中“小红帽”，只扫描主宠槽位并复用 App 端已有的背包滚动读取能力，精确核对十件目标装备；如需可恢复的脱装测试，只允许逐件操作白名单目标，测试结束必须逐件穿回并复验。
- `hao1` 至 `hao7` 只扫描当前主战宠物，不遍历或操作副宠，并验证十件目标装备是否完整穿戴。
- 验证游戏页面的一键脱装和一键穿装在正式流程中不可达，防止再次波及副宠或穿入同槽位的非目标装备。
- 扫描五类可配置背包物资。
- 记录真实日常任务确认框类型和文案。
- 在运行副本页面验证 DOM 探测周期、最近成功时间，以及预览分辨率、目标/实际刷新率、最近帧、丢帧数和页面稳定状态均可回报。
- 不上架、不购买、不运行副本。

### C. 单账号功能测试

- 在用户确认后，只测试一个账号的日常任务、四副本、背包快照和圣殿恢复。
- 验收成功后才进行装备真实交易。

### D. 两账号交接测试

- 先测同设备交接，再测跨设备交接。
- 每次只转移测试清单中的装备，确认卖方清空、买方完整、无重复购买。

### E. 八账号全链路

- 用户明确确认后手动启动一次。
- 全程允许中断和从明确阶段恢复。
- 最终必须验证十件装备回到 `hao`，八账号今日记录全部完成。

## 9. 开发顺序建议

1. 只读装备归属扫描和背包快照。
2. 日常任务确认的真实文案采集与验证式修复。
3. 中继端持久化计划状态与模拟测试。
4. Android 结构化阶段遥测和幂等命令。
5. 控制台每日计划、监控表和手动刷新。
6. 单账号、同设备双账号、跨设备双账号、八账号全链路逐级验收。
